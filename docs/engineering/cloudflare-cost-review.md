# Cloudflare上の処理量を仕様・テスト・運用で確認する

対象はマイル残高と、その呼出し元・定期処理。性能テストの成功は、請求額の上限や本番の全機能の安全を保証しない。

## 開発者の入口（実装前 → PR前）

1. 実装前に下の設計メモを仕様へ貼る。未測定は仮定と区別して残す。
2. ローカルで `pnpm install --frozen-lockfile` 後に **`pnpm check:cost`** を実行する（Node 20以上・Python 3が必要、Cloudflare認証不要）。
3. 新しいSQL・呼出し元を追加したら、実際の関数を呼ぶ性能テストも追加する。既存の残高テストだけで全機能を検査できるわけではない。

```text
処理の入口・利用者/テナント数・頻度：
1操作のSQL回数 × 対象行数（read/write）・索引の根拠：
同時実行・再試行/ポーリングの上限と、日次の呼出し回数：
無関係な履歴／本人履歴／人数／頻度が各100倍・1000倍になる場合：
Workers request/CPU と D1 rows の測定値・仮定・共有無料枠：
実際の関数を通るテスト・悪い実装が失敗する証拠：
```

### どこで止まるか

- 全PR・merge queue・main pushで、変更パスによらず `Cost Safety` チェックを実行する。fork PRも秘密情報なしで実行できる。GitHub Actions自体の初回承認待ち・skip指示は検査成功ではない。
- 対象ワークフロー（`deploy-cloudflare-worker.yml`・`release.yml`）では、同じ `pnpm check:cost` が失敗したら後続のDB変更・アップロードへ進まない。ローカルの `pnpm deploy:worker` / `pnpm --filter worker deploy` も先に実行する。
- **マージ禁止の強制は別設定**。mainのrequired status checkに GitHub Actionsの `Cost Safety` を追加し、最新mainでの成功を必須にする必要がある。この変更では保護設定・権限を変更しない。
- 直接のwrangler/API操作、既に作成済みの古いbundle、旧版のワークフローには遡及しない。Cloud promoteはbundle作成時の成功を確認するため、適用前のbundleは別途検証が必要。
- この検査は処理量の回帰を防ぐもの。D1実課金rowsや月額上限を保証しない。

## 今回の構造と、見逃した点

確認できた構造は「対象者を列挙 → 対象者ごとに残高集計 → プログラム全体の台帳を読み、本人条件で除外」。利用者単位の仕事に、利用者以外の履歴量が掛け合わされていた。Camp側の毎分ジョブは最大20人、各人2プログラム、5分より古いsnapshotを更新する。人数のLIMITやsnapshotがあっても、内側のSQLの読み取り範囲は小さくならない。画面から古いsnapshotを更新する経路もある。

これはループ中の集計による増幅であり、個々の台帳行を追加取得する典型的なN+1だけの問題ではない。修正は本人・紐付きfriendのIDを既存索引で取得し、UNIONで重複排除してから集計する。本人の履歴そのものが増えた場合は引き続き処理量が増える。

修正前の関連テストは少量fixtureで金額・状態・本人紐付けを検証していた。結果が正しい全体走査も通るため、これでは処理量の回帰を検出できない。今回追加した実行計画テストに加え、データ量を変えた動的テストを追加する。既存のCIにこの規模の検査はなかった。過去のレビューで何を確認したか、アカウント側の通知設定が当時どうだったかは未確認であり、担当者の見落としと断定しない。

## 仕様・設計レビューで必須にする項目

SQL、Cron、ポーリング、再試行、集計対象・索引を変更するPRは次を埋める。該当しない項目にも理由を書く。

1. 処理の単位：1人・1テナント・1注文・全体のどれか。SQLの絞り込みと索引の先頭列がその単位と一致するか。共有DBとテナント別DBを区別する。
2. 呼出し回数：入口、周期、対象人数、プログラム数、再試行上限、同時起動、画面経由、失敗時の再選択を数える。クエリ1回が速くても、呼出し回数が増えれば課金は増える。
3. 1回の量：D1の `meta.rows_read/rows_written`、Workersのrequest/CPU時間を測定する。返却行数・SQL件数・応答時間を課金行数の代わりにしない。索引の更新もwriteを増やす。
4. 増加軸を別々に確認：無関係な履歴、本人の履歴、利用者数、テナント数、実行頻度。それぞれ1倍・100倍・1000倍。すべてを同時に増やす場合は掛け算になる。バッチ上限で頭打ちになる場合は遅延・滞留件数を示す。
5. 正しさ：付与・利用・取消・失効・pending/void・本人統合/解除・重複イベントを保つ。キャッシュや事前集計を導入するなら全ての書込経路、再構築、並行実行、補正の契約を先に決める。
6. 費用：プランとアカウント全体の使用量、契約期間を明示する。無料枠を機能・テナントごとに重複適用しない。StandardとWorkers for Platformsを混同しない。
7. 上限・復旧：月次予算、注意/緊急閾値、担当、承認済みの停止単位、利用者への影響、復旧・ロールバック手順。未承認の顧客停止やポイント抑制はしない。

定期処理の概算は `日次rows = 日次実行回数 × 1回の対象人数 × 対象ごとのクエリ数 × クエリの平均rows`。Cronの最大40残高/分なら最大57,600残高/日だが、これは残高SQLだけの上限であり、付随SQL・画面経由・再試行・重複起動は別に計上する。対象人数が増えて上限に達すれば、処理量が止まっても更新の遅延が増える。

## CIで実行する検査

`pnpm --filter @line-crm/db test:cost` はproduction helperを呼んで実際のSQLとbindを記録し、現在のbootstrap schemaを使うローカルSQLiteで実行する。コピーしたSQLや本番データを測らない。

- 無関係なfriend/ledgerを100、10,000、100,000行に増やし、本人24行と空の財布の処理量がほぼ一定か検査する。
- 本人の履歴を24、2,400、24,000行に増やし、期待どおり線形に増えるか、金額が正しいか検査する。
- helperのSQL回数を固定し、行ごとの追加取得を検出する。
- 索引を落とす負例で、検査が実際に悪化を検出できることを確認する。
- 単位はSQLite VM命令数。**D1課金rows、Workers CPU ms、請求額ではない**。実行時間の揺れだけで合否を決めない。本番D1の実行計画と低負荷の実metricsで補完する。

Cost Safetyワークフローは公開資格情報なしで実行し、bootstrapの同期、スケール検査、残高の正しさ、費用計算・監視判定を確認する。PRチェックとして表示されるが、ブランチ保護のrequired check化は別の管理設定であり、この変更では操作しない。

`node scripts/cost/cost-model.mjs scripts/cost/assumptions.example.json` は入力された実使用量または明示的な仮定から1/100/1000倍の追加従量料金を計算する。例の数値は架空で、承認済み予算でも本番予測でもない。DB/storage/script数、基本料、他サービス、税・為替は含めない。CPU未測定を0と置いて「安い」と結論しない。

## 低負荷の監視と対応

`scripts/cost/d1-watch.py` は既存権限のGraphQL Analyticsを1アカウントにつき1回読み、アカウント全体のread/write行数と対象残高SQLを分けて出力する。業務DBへ集計SQLを発行しない。最後の10分を除いた1時間を観測し、EXPLAINを除く。SQL本文や顧客識別子は出力しない。欠測・権限エラー・上限到達はunknownであり、0円/正常として扱わない。

運用案は毎時1回、2回続けて予算または残高1回あたりのrowsが閾値を超えたら担当へ通知。大幅増加は最初の1回でも注意表示する。日次でaccount全体、週次で上位query形状と呼出し回数を確認し、Workers request/CPU、D1 storage、他サービスも別途照合する。閾値は安定した観測期間の実測と承認済み予算から設定し、固定値を請求上限と扱わない。

本変更はcollectorと判定を実装するが、実行スケジュール・通知先・新しい認証・課金サービス・自動停止は登録しない。通知先、予算、担当の承認後に既存運用へ接続する。アラートは検知手段であり、請求停止や課金上限を保証しない。CPU時間制限もD1の月次rows上限ではなく、設定変更で処理を中断する影響をレビューする。
